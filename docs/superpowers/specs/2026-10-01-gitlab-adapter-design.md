# GitLab adapter (node) — Design

Status: design approved in conversation, pending review of this spec

## Purpose

repokeeper applies one repository standard, but only to GitHub. This work
completes the phase 2 item "a GitLab adapter" of the original design
(`2026-09-25-repokeeper-design.md`, section 12) far enough to prove the
approach on a real project: a node repository on gitlab.com gets the same
standard, generated by `repokeeper init`, and `repokeeper check` keeps it
there.

There is no existing GitLab repository waiting for this. Success is a demo
node repository on gitlab.com with a green merge request pipeline and one
real release made by the generated configuration.

## Scope

In scope (this spec, "Spec A"):

- `platform: gitlab` in the configuration, and a `gitlab` platform adapter.
- Community files, CODEOWNERS and Renovate configuration.
- `.gitlab-ci.yml` with the jobs for the node stack, commit linting,
  drift checking, releasing and Renovate.
- Releases with semantic-release.

Out of scope:

- `repokeeper gitlab apply` (protected branches, approvals, pipeline
  schedules, CI variables). It calls the GitLab API instead of writing files
  and gets its own spec ("Spec B").
- Stacks other than node. They are added in later rounds, as they were for
  GitHub.
- Publishing packages to a registry. repokeeper does not do it on GitHub
  either.
- Windows or macOS runners on GitLab.

## Decisions taken

| Topic | Decision |
| --- | --- |
| Where CI logic lives | Generated into the target repository's `.gitlab-ci.yml`. No CI components and no remote includes, so it also works on a self-hosted GitLab |
| First stack | node only |
| Release tool | semantic-release (chosen earlier) |
| Dependency updates | Renovate, run from a scheduled pipeline of the repository |
| Standard version | Stays `1.4.3`: no output of a GitHub repository changes |
| Release | repokeeper `0.5.0` (a `feat`) |

## Configuration and platform selection

- `platform` accepts `"github"` or `"gitlab"` (schema and `RepokeeperConfig`).
- `init` picks the platform in this order:
  1. `--platform <github|gitlab>` when given;
  2. `gitlab` when the host of the `origin` remote contains `gitlab`;
  3. `github` otherwise (today's behaviour, including no remote).
- `--platform` is rejected with a usage error on commands other than `init`,
  and for any other value.
- `parseRemoteUrl` learns GitLab remotes, HTTPS and SSH. A GitLab project can
  live in nested groups (`group/sub/project`): `owner` is the whole namespace
  path (`group/sub`) and `name` the last segment. It also returns the host,
  which `RepoInfo` carries as `host: string | null`, because a self-hosted
  GitLab has its own.
- The default branch other than `main` is stored under `gitlab.default_branch`,
  as `github.default_branch` is today. `defaultBranch(config)` reads the key
  of the configured platform. The `gitlab` key holds nothing else in this
  spec; Spec B adds settings to it.
- A `github:` key in a gitlab configuration, or a `gitlab:` key in a github
  one, is a validation error that names the key.
- `repokeeper github apply` on a gitlab repository fails with
  "this repository uses the gitlab platform".

`buildContext` selects the adapter from `config.platform`.
`PlatformAdapter.id` becomes `"github" | "gitlab"`.

## Unsupported stacks

A gitlab configuration naming a stack other than `node` fails `init`,
`check` and `update` with:

`stack "<id>" is not supported on gitlab yet (supported: node)`

It fails instead of leaving the CI job out, because a repository that looks
managed but has no CI is worse than a clear refusal. `init` with stack
detection reports the same error when it detects such a stack.

## Outputs on GitLab

Modules that do not go through the adapter (editorconfig, commits, hooks,
gitignore, LICENSE, CONTRIBUTING, CODE_OF_CONDUCT) are unchanged.

### Community files (`communityFiles`)

- `.gitlab/issue_templates/Bug.md` and `.gitlab/issue_templates/Feature.md`:
  Markdown with the same questions as the GitHub forms, ending with the
  quick actions `/label ~bug` and `/label ~enhancement`.
- `.gitlab/merge_request_templates/Default.md`: the same Summary / Testing
  checklist as the GitHub pull request template.
- `.gitlab/CODEOWNERS`, when `health.codeowners` is not empty: `* <owners>`.
- No equivalent of `ISSUE_TEMPLATE/config.yml`; GitLab has none.

### Text that names the platform

- `SECURITY.md` on GitLab asks reporters to open a **confidential issue**
  at `https://<host>/<owner>/<name>/-/issues/new?issue[confidential]=true`
  instead of pointing at GitHub security advisories. Without a known remote
  it keeps the existing fallback wording.
- `init` writes the health `contact` as `https://<host>/<owner>` on GitLab.

These two are the only places outside the adapter that build a GitHub URL;
they take the URL from the adapter (a new `securityContact(repo)` /
`profileUrl(repo)` pair) so no module tests the platform id itself.

### Dependency updates (`dependencyUpdates`)

`renovate.json`:

- extends `config:recommended`;
- weekly schedule;
- minor and patch updates grouped per manager;
- `semanticCommitType: "chore"`, with the scope kept, so commits pass
  commitlint;
- major updates of `@types/node` disabled, as in the Dependabot config.

The ecosystems argument (Dependabot names) is not needed: Renovate detects
managers itself. The adapter ignores it.

### CI (`ciWorkflow`) — `.gitlab-ci.yml`

Written as managed YAML keys (the existing `yaml` output kind), so jobs and
keys the user adds to the file are kept.

- `workflow.rules`: run for merge request pipelines, for the default
  branch, and for scheduled pipelines; nothing else. This also prevents the
  duplicate branch + merge request pipeline.
- `stages`: `test`, `release`.
- `node` (stage `test`): `parallel: matrix` over `NODE_VERSION` (the stack's
  versions, default 22 and 24), image `node:${NODE_VERSION}`. It runs the
  stack's install command, then each configured script that exists, the
  same list the GitHub reusable workflow receives. pnpm and yarn are enabled
  through corepack before the install. The npm cache directory is cached,
  keyed on the lock file. Not run in scheduled pipelines.
- `commits` (stage `test`, when the commits module is on): installs the same
  pinned commitlint as the GitHub workflow and checks
  `$CI_MERGE_REQUEST_DIFF_BASE_SHA..$CI_COMMIT_SHA` in a merge request
  pipeline, the last commit otherwise. `GIT_DEPTH: 0`. Commits authored by
  the Renovate bot follow the semantic prefix, so no ignore rule is needed.
- `repokeeper` (stage `test`, when the drift module is on):
  `npx repokeeper@<PACKAGE_VERSION> check`.
- `release` and `renovate`: below.

The node stack's `os` option has no effect on GitLab. `init`, `check` and
`update` print one note when it is set to anything other than
`ubuntu-latest`: "node.os is ignored on gitlab (Linux runners only)".

The adapter reads the node stack's existing `ci.with` values (versions,
install command, package manager, scripts). `CiJob` keeps its shape; a
neutral CI description is deferred until a second stack shows what it has
to hold.

### Release (`releaseAutomation`)

- `.releaserc.json` (managed file):
  - `branches`: the default branch;
  - `tagFormat`: `v${version}`;
  - plugins, in order: commit-analyzer and release-notes-generator with the
    `conventionalcommits` preset; changelog (`CHANGELOG.md`); npm with
    `npmPublish: false` (bumps `package.json` and the lock file); git
    (commits `CHANGELOG.md`, `package.json` and the lock file present, with
    the message `chore(release): ${nextRelease.version} [skip ci]`); gitlab
    (creates the GitLab release).
- `release` job (stage `release`): only on the default branch, not in
  scheduled pipelines, and only when the CI variable `GITLAB_TOKEN` is set.
  It installs pinned versions of semantic-release and its plugins into a
  temporary directory, as the commitlint job does, and runs it. `GIT_DEPTH: 0`.
- semantic-release's versions are pinned in `TOOL_VERSIONS`, next to
  lefthook and commitlint.
- No release-please files are produced on GitLab, and no `marker` output:
  node has no `versionLine`.

Behaviour that differs from GitHub, to be stated in the README: there is no
release pull request. Every push to the default branch containing a `feat`,
`fix` or breaking change releases at once. A repository without a version
tag gets `1.0.0` as its first release (semantic-release's rule); to continue
from an existing version, tag it `vX.Y.Z` first.

`GITLAB_TOKEN` is a project access token with the `api` and
`write_repository` scopes and a role allowed to push to the default branch.
Creating it and the variable is manual until Spec B.

### Renovate job

`renovate` (stage `test`): only in scheduled pipelines and only when
`RENOVATE_TOKEN` is set. It runs the pinned `renovate/renovate` image
against `$CI_PROJECT_PATH` on `$CI_API_V4_URL`. The pipeline schedule and
the token are created by hand until Spec B. Without them the job never
runs and nothing fails.

## Error handling

Covered above: unknown `--platform` value; platform key mismatch in the
config; unsupported stack; `github apply` on a gitlab repository. All are
`UsageError` or config errors with exit code and wording consistent with the
existing ones. No new network access: this spec only writes files.

## Testing

- `test/platforms-gitlab.test.ts`: each adapter method — community files and
  CODEOWNERS; `renovate.json`; `.gitlab-ci.yml` keys for npm, pnpm and yarn
  projects, custom node versions and scripts, commits/drift off, default
  branch other than `main`; `.releaserc.json` and the release job.
- GitHub outputs are pinned unchanged by the existing tests; no GitHub
  expectation is edited.
- Config: schema accepts `gitlab`; mismatched platform key rejected;
  `defaultBranch` per platform.
- `parseRemoteUrl`: gitlab.com and self-hosted, HTTPS and SSH, nested groups.
- Health: `SECURITY.md` and `contact` on GitLab.
- Unsupported stack error; the `node.os` note.
- e2e: `init --platform gitlab` on a node repository writes the files above
  and none under `.github/`; `check` then exits 0; `init` with a GitLab
  `origin` selects gitlab without the flag.
- Generated `.gitlab-ci.yml` is parsed back as YAML in tests. Its validity
  as a GitLab pipeline is only proven by the pilot.

## Pilot and rollout

1. Release repokeeper `0.5.0`.
2. Create `repokeeper-demo-gitlab-node` on gitlab.com (needs the user's
   account and an access token), run `init`, open a merge request, confirm a
   green pipeline.
3. Add `GITLAB_TOKEN`, merge a `feat`, confirm the tag, the GitLab release
   and the changelog commit.
4. Add `RENOVATE_TOKEN` and a schedule, confirm Renovate opens a merge
   request whose commit passes the `commits` job.

Findings from the pilot are fixed before any further stack is added.

## Open risks

- The generated pipeline is not validated against GitLab until the pilot.
- semantic-release pushes a commit to the default branch; a protected
  default branch must allow the token's role to push. Spec B will configure
  it; until then it is a documented manual step.
